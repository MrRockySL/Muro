## Context

See `proposal.md` — Why. Rebased on **upstream v4.0.3** (`1aa1603`).

Current state (v4.0.3):

- `AutomationScheduler` owns one timer for the running playlist or automation. Its `apply` callback is `((String) -> Void)?` (`AutomationScheduler.swift:25`) and `AppStore` wires it (`Store.swift` ~317-321) to `setWallpaper(item, mode:)` with no `surface`, so `applyWallpaper` (`Store.swift:962`) resolves `surface = explicitSurface ?? .desktop` and only ever calls `applyAssignment` (the engine window). The `apply?` call sites are `AutomationScheduler.swift` lines 122, 143, 147, 194, 198.
- `LockScreenService.apply(entry:videoURL:thumbnailURL:target:surface:connectedDisplays:)` (`LockScreenService.swift:416`, `surface` defaults to `.desktop`) is the only path to the lock screen. Per call it sets the per-display selection via `LockScreenSelections.afterApply(current:targetKey:wallpaperID:connectedDisplays:)`, stages the video into the extension container, writes `Index.plist` + `Index2.plist` (looped up to 3×, with sleeps), runs `registerExtension`, and restarts `WallpaperAgent` while awaiting an acquire receipt. Worst case several seconds plus a system-wide wallpaper flash.
- **`LockScreenSelections`** (`MuroKit/LockScreenSelections.swift`, new in v4.0.3) keeps **one selection per connected display**: `afterApply` with `targetKey == "all"` returns `["all": wallpaperID]`; otherwise it keeps the `all` entry plus per-display entries for still-connected displays and sets `next[targetKey]`. `LockScreenService` stores this as `SelectionState { selections: [String:String]; screenSaver: [String:String] }`; `heldIDs(_:)` is the union of both maps minus `__none__`, and `pruneStagedLibrary(keeping:)` keeps only staged dirs in that set.
- `LockScreenService.ownsWallpaperSurface(displayUUID:)` returns true when `state.selections[displayUUID] ?? state.selections["all"]` is non-nil and not `__none__`.
- **`DesktopStillService`** (`MuroApp/DesktopStillService.swift`, the v4.0.3 rewrite of `DesktopTintService`; state file still `desktop-tint.json` for install compatibility) writes a still frame of the current wallpaper as the real macOS desktop picture. Its one entry point is `reconcile(config:manifest:lockScreenDisplays:)`, called from `AppStore` after applies/steps. Its `set(_:on:screen:uuid:isLockScreenOwned:)` **skips a display** when `isLockScreenOwned` (the uuid is in the `lockScreenDisplays` set the caller passes, sourced from `lockScreenOwnedDisplays` → `ownsWallpaperSurface`) **or** the current desktop image path contains the extension bundle id.
- The extension (`MuroWallpaperExtension`) holds a live `CAContext` + root `CALayer` + `VideoRenderer` per `WallpaperSurfaceKey` in `RendererState.shared.active` while `RendererState.shouldPlayNow()` is true. With `alwaysPauseDesktop` (always set by `LockScreenService`), that is true only when `presentationMode == "locked"`. `ExtensionPlaybackCoordinator` (in `ExtensionPreferences.swift`) flips the mode on `com.apple.screenIsLocked` / `screenIsUnlocked` via `DistributedNotificationCenter`.
- `ActiveWallpaper` (`RendererState.swift`) holds `context`, `rootLayer`, `renderer`, `choiceID` all as `let`. `VideoRenderer` (`VideoRenderer.swift`) holds `asset` (`AVURLAsset`) and `videoTrack` (`AVAssetTrack`) as `let`; `static func create(rootLayer:videoURL:)` builds one and adds its `AVSampleBufferDisplayLayer` as a sublayer of `rootLayer`; `stop()` removes that sublayer. `RendererState.install(_:for:)` swaps the entry and calls `previous?.renderer.stop()`. `RendererState.lifecycleQueue` is a serial `DispatchQueue`.
- On `acquire`, macOS hands the extension the `Configuration` bytes from the store choice; `SettingsProvider` / `main.swift` read them as the wallpaper id (a bare lowercased UUID string) and look up the staged video. Every extension reader of that id — `stagedVideoURL(for:)`, `soleStagedChoiceID()`, the `AcquireReceipt.id` match, `SettingsProvider`'s `ChoiceIDDescriptor` — does plain string equality. `library.json` in the container lists staged entries as `ExtensionWallpaperEntry { id, title, videoFilename, thumbnailFilename }`.
- `LockScreenService.notifyLibraryChanged()` already posts `com.mrrockysl.muro.wallpaper.library-changed` on the **Darwin notify center** (`CFNotificationCenterGetDarwinNotifyCenter()`) after store writes and at the end of `pruneStagedLibrary` — **no code in the extension observes it today**. The extension *does* already observe a sibling Muro notification on that same center: `ExtensionPreferences.init` registers a `CFNotificationCenterAddObserver` for `com.mrrockysl.muro.wallpaper.preferences-changed` and calls `reloadAndApply()`.
- `enum ApplySurface` lives in `MuroApp` (`Store.swift:58`), is `String, CaseIterable`, is **not** `Codable`, and its cases are `.all` (`"All"`) / `.desktop` (`"Desktop"`) / `.lockscreen` (`"Lockscreen"`) / `.screensaver` (`"Screensaver"`). `coversDesktop` / `coversLockScreen` / `coversScreenSaver` and `appleSurfaces: [AppleWallpaperStore.Surface]` are computed. `AppleWallpaperStore.Surface` is `.desktop` / `.screenSaver` only — the lock screen has no key of its own and renders the desktop role. `MuroKit`'s `Playlist` / `Automation` cannot reference `ApplySurface` as written.
- macOS 26+ gate and the `DesktopStillService` fallback already hide the single lock-screen apply UI; the surface picker rides the same `store.lockScreenAvailable` and the existing `PreviewView.surfacePill` pattern.

## Goals / Non-Goals

**Goals:**

- One rotation step that touches the lock screen costs: replace one file behind a fixed id + post `library-changed` + a renderer rebuild on the live layer. No plist rewrite, no `killall WallpaperAgent`, no flash.
- One clock: the desktop and lock-screen halves of a schedule move on the same `AutomationScheduler` tick, so they cannot drift.
- Failure of the new path degrades to "lock screen keeps the last wallpaper", never a blank screen.

**Non-Goals:**

- Changing desktop rotation. It stays on the engine path.
- Making a plain (non-rotation) lock-screen wallpaper hold a still. The lock screen plays its video; only the desktop freezes on a frame. The pause fix (tasks 4.8/4.9) freezes the locked video only while Muro is explicitly paused. A general "keep the lock screen still like the desktop" preference is a separate change if wanted — user confirmed 2026-09-10 to leave it as is.
- Independent playlists per surface (different lists / intervals for desktop vs lock screen). One schedule, one order, one interval.
- An extension-side rotation timer or a second clock (rejected by the maintainer in #26; see D1).
- **Screen-saver rotation.** The screen saver ships as its own static surface in **v4.0.3** (upstream #18). #26 deliberately does not rotate it: `ApplySurface.screensaver` is not offered in a schedule's picker, and a schedule's `.all` fans out to Desktop + Lock Screen only, never `AppleWallpaperStore.Surface.screenSaver`.

## Decisions

### D1: The app's existing timer does the swap; the extension only listens

`LockScreenService` writes the Apple store **once** when a lock-screen schedule starts, with a **fixed wallpaper id** — the schedule's own UUID (`playlist.id` / `automation.id`), a bare lowercased uuid string, see D6 — that never changes for the life of the schedule. Each `AutomationScheduler` tick for a schedule whose `surface` covers the lock screen **replaces the video file behind that id** in the extension container and posts the existing `library-changed` Darwin notification. The extension grows a `library-changed` observer that re-resolves the current staged file and rebuilds the renderer on the live layer.

- No per-step plist writes, no per-step agent restarts, no flash: the store already points at the id and the id is stable.
- No second clock: the same tick drives both surfaces; the extension never computes "which step is now", it renders whatever file the app's tick just staged.
- The container holds **one rotation video**, not the whole playlist and not a window of it.

*Alternatives considered (both rejected on the issue):*
- **Pre-staged window + manifest + extension-side timer (original direction B).** Works, but needs a second clock kept in sync by hand, a manifest contract, and a look-ahead pruner. The maintainer pointed out the single-clock design makes all of that unnecessary.
- **Full `LockScreenService.apply()` per step.** Unshippable cost (seconds + flash + plist rewrites + restart), the premise of this whole change.

### D2: Stage one video; prefer a hard link

On each tick the app stages the current step's video behind the fixed id: write to a temp name in the container, then **rename over** the staged path (atomic), update `library.json`, post `library-changed`. `stageRotationStep` reuses the shape of today's `LockScreenService.stage(entry:videoURL:thumbnailURL:)` — a `.staging-<uuid>` temp directory plus an atomic `replaceItemAt` / `moveItem` and a `library.json` rewrite — with `copyItem` swapped for `linkItem` and `copyItem` kept in the `catch`. Staging prefers a **hard link** from the library file into `videos/<rotationID>/wallpaper.mov` (same volume ⇒ free: no extra disk, no copy latency); fallback is a plain copy of that one video.

- **Spike first (task 6.8, `@needs-human`):** prove the extension plays through a hard-linked file. The maintainer verified linking itself works on the same volume but has not proved playback. If playback fails through a link, the copy fallback already ships — still one small file per swap, far below the old per-step apply cost.
- A swap that fails (video missing, unreadable) leaves the previous file in place; the lock screen keeps the last wallpaper and the failure is logged.
- The staged dir survives `pruneStagedLibrary` because the rotation id is in `SelectionState.selections` (`heldIDs` union), so pruning it out is not a risk while the schedule runs.

### D3: Extension-side changes are minimal — an observer and a swap

- **`ExtensionPreferences.swift`** grows a second `CFNotificationCenterAddObserver` on `CFNotificationCenterGetDarwinNotifyCenter()` for `com.mrrockysl.muro.wallpaper.library-changed`, registered exactly like the existing `preferences-changed` observer — **not** `DistributedNotificationCenter` (that center carries `com.apple.screenIsLocked`). This keeps the change inside an existing file: no `project.pbxproj` edit. On signal, for each `ActiveWallpaper` in `RendererState`, re-resolve the staged path for its `choiceID` and call the swap when the file the renderer was built on is no longer the one on disk.
- **How "no longer the one on disk" is detected.** `stageRotationStep` renames a new file *over* the same staged path (`videos/<id>/wallpaper.mov`, fixed name — D2), so the URL string never changes and a URL compare cannot see a swap. The observer instead records, per `ActiveWallpaper`, the staged file's **identity at renderer-build time** — its inode number and size from a single `stat` — and on `library-changed` re-`stat`s the path: a changed `(inode, size)` (or the path now resolving elsewhere, or the file gone) means swap; an unchanged identity means no-op. No `mtime`, no date math, no new file — two integers on an in-memory object.
- The swap: `VideoRenderer.asset` / `videoTrack` are `let`, so no in-place repoint. Keep the `CAContext` + `rootLayer` from the existing `ActiveWallpaper` and build a **fresh `VideoRenderer`** via `VideoRenderer.create(rootLayer: existing.rootLayer, videoURL: newURL)` on `RendererState.lifecycleQueue`, wrapped in a `CATransaction`. Build a fresh `ActiveWallpaper` reusing the old `context` and `rootLayer` (and `drawsStill` / `displayID` / `isScreenSaverSurface`), then `RendererState.shared.install(new, for: key)` — which stops the old renderer and removes its sublayer. Keeping the context/root layer alive is what avoids a re-`acquire` and the flash. If `VideoRenderer.create` throws, keep the current `ActiveWallpaper` and `extensionLog` — the lock screen keeps the last wallpaper.
- `acquire` keeps resolving `Configuration` → id → staged video exactly as today; the id just happens to be rotation-owned and its staged file gets replaced underneath.
- Guard: the observer does its work only while `presentationMode == "locked"`; unlocked, the renderer is paused and decodes nothing, so a stale staged file is harmless until the next lock (D5 covers the frame shown on lock).

### D4: Surface stored on the model; the scheduler tick fans out

First, **`ApplySurface` moves from `MuroApp/Store.swift` to `MuroKit` and gains `Codable`** so the models can carry it. All four cases and their raw values (`"All"` / `"Desktop"` / `"Lockscreen"` / `"Screensaver"`) stay exactly as written — they become persisted. Add `static let scheduleCases: [ApplySurface] = [.desktop, .lockscreen, .all]` for the schedule pickers (the screen saver is never a schedule target). `MuroApp` references (`applySurface`, `setWallpaper`, `applyWallpaper`, `PreviewView`, `isApplied`) move to the relocated type.

`Playlist` / `Automation` then get the field. Both use synthesized `Codable` today, so rather than hand-writing `init(from:)`, store it as an **optional backing field with a computed accessor that defaults to `.desktop`** — the same pattern `Automation.Step` already uses (`seconds: Int?` exposed as `var duration`). A legacy blob with no `surface` key decodes fine and reads as `.desktop`, so **all legacy and new schedules start as `desktop`** — the lock screen is only ever written when the user opts that schedule in via the editor's Desktop / Lock Screen / All control.

`AutomationScheduler.apply` becomes `((_ id: String, _ surface: ApplySurface, _ target: ApplyTarget) -> Void)?`; every `apply?` call site passes the running schedule's `surface`. `AppStore` routes each tick:

- `surface.coversDesktop && !surface.coversLockScreen` (`.desktop`) → today's `applyAssignment` only, byte-identical to now.
- `surface.coversLockScreen && !surface.coversDesktop` (`.lockscreen`) → `stageRotationStep` + `library-changed` only, no engine assignment.
- `surface.coversDesktop && surface.coversLockScreen` (`.all`) → engine assignment **and** staged swap, on the same tick.

The rotation path **never** consults `surface.appleSurfaces` or `surface.coversScreenSaver` — a schedule's `.all` is Desktop + Lock Screen, and the lock-screen half always writes the Apple `.desktop` role. Only start/stop/edit touch the store (`beginRotation` on start, `remove()` teardown on stop); steps never do.

### D5: Catch-up hook, still one clock

A tick can be missed while the Mac naps or sleeps (App Nap, `scheduleWaking` edges). On `com.apple.screenIsLocked` and on wake (`NSWorkspace.didWakeNotification`, which `AutomationScheduler` already observes for `reevaluate()`), if a lock-screen schedule is running, the app **reconciles**: `stageRotationStep` for the scheduler's current index (which `reevaluate()` recomputes from elapsed time) and post `library-changed`. The extension re-reads on lock anyway (fresh `acquire` / presentation-mode flip), so a stale staged file only matters for the frame shown immediately on lock. This is the single reconciliation point; the extension owns no independent notion of time.

### D6: Rotation id shape, "applied" state, and diagnostics

The fixed rotation id **is the schedule's own UUID** — `playlist.id` / `automation.id`, already a bare lowercased uuid string. It is written into `Configuration` byte-for-byte the way a wallpaper id is today, and through `LockScreenSelections.afterApply(current:targetKey: "all", wallpaperID: rotationID, connectedDisplays:)` so the selection record collapses to `["all": rotationID]`. **No extension reader of `choiceID` changes**: `stagedVideoURL(for:)`, `soleStagedChoiceID()`, the `AcquireReceipt.id` equality check, and `SettingsProvider` all keep working on a plain string. A `playlist:<uuid>` prefix was rejected precisely because it would force an audit-and-patch of every one of those readers (task 0.3 is the confirmation pass).

Because the id is indistinguishable from a wallpaper id by shape, the **app** carries the rotation bookkeeping: `LockScreenService` persists (in its state file or a sidecar) that a given selection id is rotation-owned and which schedule drives it. `isApplied(_:surface:target:)` (app) and `LockScreenService.isApplied(wallpaperID:target:surface:)` return true for the schedule's **current step** id on the lock-screen surface (asking the running schedule, not a staged file). Diagnostics (`recordDiagnostics`) log `rotation=<scheduleID>/<index>` when a rotation drives the lock screen. `purgeDeadMuroSurfaces` / `healIfNeeded` must treat a rotation-owned id as alive while its schedule is running (the persisted flag, not file existence alone) and strip a rotation id whose schedule is not running, exactly like a dead surface today.

Because the rotation id lands in `state.selections["all"]`, `ownsWallpaperSurface(displayUUID:)` is true for every display, so `lockScreenOwnedDisplays` covers them and `DesktopStillService.reconcile` skips writing a desktop picture into those slots for free — no new coordination needed there.

## Risks / Trade-offs

- **Extension won't play through a hard link.** → D2 spike (task 6.8) decides before any UI work; copy fallback is already specced and cheap for one file.
- **`library-changed` posted while the extension is mid-`acquire`.** → The swap is a rename + notification; `acquire` reads the staged path when it resolves. Worst case it picks the previous file for one frame and the next lock shows the right one. Self-healing, no blank.
- **`pruneStagedLibrary` also posts `library-changed`.** → The observer compares the staged file's `(inode, size)` against what it recorded when the renderer was built and no-ops when they match, so a prune that does not touch the rotation dir is a no-op for the observer.
- **Observer fires repeatedly during rapid manual next/previous.** → Serialize the swap on `RendererState.lifecycleQueue` and coalesce to the latest staged URL.
- **Rotation id mistaken for a dead/stale surface by `purgeDeadMuroSurfaces`.** → D6 liveness flag; covered by a test.
- **A schedule's `.all` accidentally writing the screen saver.** → D4: the rotation path never touches `appleSurfaces` / `coversScreenSaver`; the lock-screen half is hard-coded to the Apple `.desktop` role. Covered by a test (task 4.7).
- **macOS updates WallpaperExtensionKit.** → No new private API: only what `acquire` / render already touch, plus the existing Muro Darwin notification.
- **Clock: manual next/previous while unlocked.** → `advancePlaylist` updates the scheduler state; the next staged swap follows the same tick path; D5 makes the next lock land correctly.

## Migration Plan

- Additive JSON field; no migration of `playlists.json` / `automations.json` (absent → `.desktop`).
- Nothing new persists on disk after stop: the staged rotation file is removed by the `remove()` teardown; no manifest/window to clean.
- Rollback: revert the change; a leftover rotation-owned selection is stripped by `healIfNeeded()` (extend it: a rotation id whose schedule is not running is treated exactly like a dead surface today).
- Ships behind the existing macOS 26 + `lockScreenAvailable` gate.

## Open Questions

- Whether to coalesce swaps while unlocked at all (the extension decodes nothing while paused, so an early staged swap is harmless — leaning "no debounce needed beyond the `lifecycleQueue` serialization").

## Round 2: PR #34 maintainer review (2026-09-11)

The maintainer requested changes on PR #34 (`CHANGES_REQUESTED`, 2026-09-11). Kept as confirmed-good and unchanged by this round: **D1** (single clock, no extension timer) and **D2**'s hard-link staging — both explicitly praised in the review. The rest of the review breaks down into a scope complaint ("bigger than what I asked for on #26 ... one option on the card, nothing else changing. This is 24 files") and three concrete bugs found by building it, diagnosed below.

### D7: Rotation begin/end must restore Muro's own prior selection, not fall through to "non-Muro"

**The bug.** `beginRotation` (`LockScreenService.swift:629-646`) always calls `apply(target: .all, ...)`. `LockScreenSelections.afterApply` (`MuroKit/LockScreenSelections.swift:39-40`) for `targetKey == allKey` returns `[allKey: wallpaperID]` unconditionally — it has no way to remember what was in `current` before collapsing it. `endRotation` (`LockScreenService.swift:666-668`) calls `remove(target: .all, surface: .desktop)`, whose `targetKey == "all"` branch (`LockScreenService.swift:698-699`) does `selections.removeAll()` and then `restoreWallpaperStores(targetKey: "all", ...)` — but that function's whole fallback chain (`firstNonMuroSurface` at `LockScreenService.swift:1472-1482`, `crossStoreNonMuroSurface` at `1488-1496`, `defaultSurface()` at `1509-1522`) explicitly **excludes** anything `isMuroSurface` (`1434-1438`). So even if the previous selection had survived, `restoreWallpaperStores` is structurally incapable of restoring it — it only ever lands on a non-Muro surface (a pristine pre-Muro backup, a surface from the sibling plist, or Apple's hardcoded default).

**What "restore" has to mean here.** The maintainer's own words — "the lock screen wallpaper **I already had**", "**I had two** and lost both" — describe a wallpaper (or two, one per display) he had deliberately set through Muro's own single-apply / per-display flow, the same feature the v4.0.2 fix protects: *"choosing where a wallpaper goes is not a request to remove the one somewhere else — each surface keeps what it was given until it is changed or removed on purpose"* (quoted in `proposal.md`). A rotation's takeover is "changed on purpose" while it runs; stopping it has to be the matching "removed on purpose" that gives back what was there — the previous **Muro** selection, not the system default underneath it. Confirmed with Felipe (2026-09-11): restore target is Muro's own prior static/per-display selection, not the bare Apple default.

**Fix direction (decided 2026-09-11):**
- `beginRotation` snapshots the full pre-rotation `SelectionState.selections` (and `screenSaver`, untouched but carried along) before calling `apply(target: .all, ...)`, and persists that snapshot (e.g. `SelectionState.preRotationSelections: [String: String]?`) so it survives an app relaunch mid-rotation.
- `endRotation` restores that exact snapshot — writing each display's (or `all`'s) original wallpaper id back through the Apple stores — instead of routing through the generic `remove(target: .all, ...)` / `restoreWallpaperStores` non-Muro fallback.
- Because a running rotation's `pruneStagedLibrary(keeping: heldIDs)` only keeps ids in the *current* `SelectionState` (which no longer includes the pre-rotation ids once they're snapshotted out), the staged file backing a snapshotted selection can be reaped while the rotation runs. Decided (2026-09-11): `endRotation` must **re-stage** any snapshotted selection whose staged file is gone by re-copying/linking from the library master before writing the plist back — not just skip it. This needs its own container-IO verification, same class as the existing 6.8/6.9 spikes.
- The screen-saver map is never touched by a lock-screen rotation (D4 already keeps rotation off `coversScreenSaver`) — no interaction there.

### D8: A playlist's "current step" must be the scheduler's own state, not `currentAppliedID`

**The bug.** `AutomationScheduler.advancePlaylist` (`AutomationScheduler.swift:179-195`) and `reevaluate`'s playlist branch (`AutomationScheduler.swift:228-230`) derive the current index from `currentIDForOrdering?()`, wired in `Store.swift:297` to `Store.currentAppliedID`. `currentAppliedID` (`Store.swift:910-917`) reads **only** the desktop's `config.assignment` / `config.allDisplays` — it has no notion of the lock screen. A `.lockscreen`-only playlist never writes `config`, so `currentAppliedID` never matches anything in the playlist's id list, `firstIndex(of:)` returns `nil`, `current` falls back to `0` (`?? 0`), and every tick computes the same "next" step from the same starting point — the lock screen looks frozen on one step forever.

This assumption held as long as every playlist was desktop-only (in which case "what the desktop shows" and "what the playlist applied" were the same fact); it breaks now that a playlist can target the lock screen exclusively.

**Fix direction (recommended, mirrors an existing pattern):** `Automation` already solves the identical problem for automations with `stepIndex` — a scheduler-owned `Int`, persisted in `UserDefaults` (`AutomationScheduler.swift:44-61`), independent of which surface got written. Give playlists the same: a scheduler-owned, persisted "current playlist id/index" that the scheduler updates every time it actually applies a step, for every surface — not re-derived from any single surface's applied state. This removes the `currentIDForOrdering` dependency for playlist ordering entirely (it can stay for anything UI-only that legitimately wants "what's on the desktop right now").

### D9: Starting a schedule must read the scheduler's own id, not the store's mirror of it

**The bug**, found re-running manual check 8.10(a): starting a Desktop + Lock Screen (or Lock Screen–only) playlist while a wallpaper was already manually applied to the lock screen did not take it over — the desktop half switched immediately, the lock screen did not.

`AutomationScheduler.startPlaylist`/`startAutomation` (`AutomationScheduler.swift:144-154`, `129-137`) set the scheduler's own `activePlaylistID`/`activeAutomationID` and then, in the same synchronous call, invoke `apply?(...)` for the first step — which runs `Store.applyScheduledStep` → `driveLockScreenRotation` (`Store.swift:1120-1124`, before this fix). That function resolved `scheduleID` from `self.activePlaylistID ?? self.activeAutomationID` — the **store's own** `@Published` copies, which are only assigned in `syncScheduler()` (`Store.swift:675-684`), and `syncScheduler()` runs **after** `scheduler.startPlaylist(playlist)` returns (`Store.swift:1656-1659`). So on the very first tick the store's copies were still whatever they were before starting (`nil`, normally), the guard failed, and `driveLockScreenRotation` silently returned — no error, nothing staged, nothing registered. The lock screen only actually began rotating on the *second* tick, a full interval later, which is invisible when nothing was on the lock screen before (looks the same either way) but visible as "did not take over" when a manual wallpaper was already showing there.

**Fix**: read `scheduler.activePlaylistID`/`scheduler.activeAutomationID` directly in `driveLockScreenRotation` — the scheduler's own properties are `private(set)`, so the store can read them without exposing a setter, and they are always current by definition (the store's `@Published` copies exist only to drive SwiftUI bindings, not as a second source of truth).

**Not independently unit-testable**: same constraint as `LockScreenService`/`AutomationScheduler` generally (`Store` has no test target); this is a sequencing bug in when one property is copied from another, not a decision worth extracting into MuroKit. Covered by re-running manual check 8.10(a).

### D10: Editing the running schedule itself must re-apply the current step, not just re-arm the timer

**The bug**, found re-running manual check 8.10 after the D9 build: editing an *already-running* playlist — most notably turning on Lock Screen coverage, or reordering/changing its content — and pressing Save did not take effect until the user manually skipped to the next wallpaper. Reported as two symptoms that turned out to share one cause: (1) "playback doesn't start when you Save, only a manual next-wallpaper does", and (2) "locking still shows the old manual/previous lock-screen wallpaper, not the playlist's".

`AutomationScheduler.update(automations:playlists:)` (`AutomationScheduler.swift:113-125`) runs on every save via `Store.syncScheduler()`, for *any* library edit, not only edits to the running schedule. Before this fix its only three outcomes were: stop the schedule (now empty), stop it (deleted), or — in every other case, including "the running schedule's own definition changed" — just call `schedule()` to re-arm the countdown. It never re-invoked `apply?(...)` for the current step. So adding Lock Screen coverage to an already-running Desktop-only playlist saved correctly to disk and the timer kept ticking on schedule, but `driveLockScreenRotation` (the only path that calls `LockScreenService.beginRotation`) was never called for that step — the lock screen kept showing whatever was already there — and, since the same `apply?` call is what re-renders the desktop for the *edited* content (new order, different wallpaper), the desktop half didn't visibly reflect the edit either until `advancePlaylist` (the menu bar's manual next) called `apply?` directly for the first time.

**Fix**: `update` now captures the active automation/playlist *before* reassigning `self.automations`/`self.playlists`, and — only in the branch where the schedule keeps running — compares old vs. new. When the running schedule's own definition changed (`Playlist`/`Automation` are already `Equatable`), it re-applies the current step before re-arming: `applyCurrent(of:)` for an automation (already existed, used by the clock/timer paths), and a new `reapplyCurrentPlaylistStep(of:)` for a playlist, which resolves `playlistCurrentID` against the (possibly edited) `wallpaperIDs`, falling back to the first entry if the previously-current id was removed. Gating on "did the *active* schedule's definition actually change" — not "some update happened" — matters: `update` fires on every unrelated save in the library too (any other playlist's edit, any automation's edit), and unconditionally re-applying then would re-write an unchanged wallpaper on every unrelated edit, which is exactly the kind of extra WallpaperAgent churn the maintainer already asked this PR to avoid touching (see "Scope correction" below).

**Not independently unit-testable**: same constraint as D9 — `AutomationScheduler` has no test target, and this is a sequencing gap in when `apply?` gets re-invoked, not a decision worth extracting into MuroKit as pure logic (the comparison itself is just `!=` on two already-`Equatable` structs). Covered by re-running manual check 8.10.

### D11: Starting a schedule must clear the pause flag itself, not wait for a file-watcher re-sync

**The bug**, reported by the user 2026-09-11: after starting a playlist, its row in the UI shows the "play" indicator active but the schedule never advances on its own — the user has to press "advance to next wallpaper" manually to get it moving, and every subsequent tick again needs a manual nudge.

`AutomationScheduler.startPlaylist`/`startAutomation` (`AutomationScheduler.swift:172-182`) set `activePlaylistID`/`activeAutomationID`, run the first step's `apply?(...)` synchronously, and call `schedule()` (line 181) to arm the countdown Timer. `schedule()` (`AutomationScheduler.swift:284-286`) bails out with `guard !isPaused` — and `Store.startPlaylist`/`startAutomation` (`Store.swift:1666-1669`) never touch `isPaused`/`config.paused` before delegating to the scheduler. If the pause flag is `true` at that moment (left over from a previous pause, or because a concurrent manual apply's deferred `Store.applyAssignment` — the only place that clears `config.paused` — has not finished yet, see D12), the Timer never arms. The UI shows the schedule as "active" regardless (it reads `activePlaylistID`, set unconditionally), with no way to tell the Timer didn't start. The only path that calls `apply?(...)` again after that is `advancePlaylist`'s manual "next" (`AutomationScheduler.swift:225`), which applies the next step directly and bypasses `schedule()`/`fire()` entirely — explaining why one manual click "fixes" it without re-arming anything.

**Fix**: `Store.startPlaylist`/`startAutomation` now force the pause state to `false` (`config.paused = false`, `saveConfig()`, `scheduler.setPaused(false)`) before delegating to `scheduler.startPlaylist`/`startAutomation`, so `schedule()`'s guard always sees `!isPaused` on a fresh start regardless of whatever the flag held before.

**Not independently unit-testable**: same constraint as D9/D10 — `Store`/`AutomationScheduler` orchestration has no test target. Covered by a manual check added to 8.10's scope: start a playlist/automation right after leaving one paused, confirm it advances across ticks with no manual "next" needed.

### D12: Concurrent applies must not let a stale write clobber a newer one

**The bug**, reported by the user 2026-09-11: manually applying a wallpaper "to all displays" (Desktop + Lock Screen), then immediately starting a playlist with Apply-to = All, produces no visible change at all — not even on the desktop.

`Store.applyWallpaper(_:mode:target:surface:)` is `async`; for `surface == .all` it awaits `lockScreen.apply(...)` once per connected Apple surface (`Store.swift:1038-1046`) — a call that can take on the order of several seconds (`LockScreenService`'s up-to-3-pass `restartWallpaperAgent` retry loop) — and only *after* that await does it call `applyAssignment` (`Store.swift:1049-1050`), the function that writes `config.allDisplays`/`config.paused = false` to disk. Nothing serializes two overlapping `applyWallpaper` calls: if the user starts a playlist while an earlier manual "apply to all" is still awaiting its lock-screen writes, the playlist's own first-step `applyAssignment` can land first, and the earlier, still-in-flight manual apply's deferred `applyAssignment` then finishes afterward and overwrites `config.json` back to the manually-applied id — reverting both surfaces to the old wallpaper with no error and no visible transition.

This is the most plausible explanation supported by the code (no serialization exists between overlapping applies, and the overlap window — several seconds — is well within ordinary "apply, then immediately start a playlist" usage); it has not been confirmed via a runtime timing reproduction, only by tracing the call sites. The fix is additive and only changes behavior when two `applyWallpaper` calls genuinely overlap, which under the current code can never produce a correct result anyway.

**Fix**: `Store` gains a monotonically increasing `applyGeneration` counter. `applyWallpaper` captures its own ticket at entry; the per-surface lock-screen writes and the trailing `applyAssignment` call each check the ticket is still current before writing, and bail out silently if a newer `applyWallpaper` call has since started. The newest call to *start* always wins, regardless of which happens to *finish* last.

**Not independently unit-testable**: `Store` has no test target and this is concurrency sequencing, not decidable pure logic. Covered by a manual check added to 8.10's scope: apply a wallpaper to all displays, immediately (within a few seconds) start a playlist, confirm the playlist's first step wins on both surfaces.

### D13: A manual apply mid-rotation must drop the stale rotation pointer it just orphaned

**The bug**, reported by the user 2026-09-11: with a playlist actively running, manually applying a wallpaper to any screen/mode leaves the row's "play" indicator on, but the *next* scheduled tick no longer updates the lock screen — unless the playlist is stopped first before the manual apply, in which case the following manual apply works cleanly.

`LockScreenService.apply(...)` writes the Apple wallpaper store's selection for `surface`/`targetKey` unconditionally (`LockScreenService.swift:505-514`), regardless of whether a rotation currently owns that store. Only when the caller passes `rotation: true` does it also record `nextState.rotation = storeID` (`LockScreenService.swift:515-518`); a manual apply always passes `rotation: false` (the default) and a fixed `storeID = entry.id`, never the schedule's id (`Store.swift:1040-1044`). So a manual apply while a rotation is active overwrites the very store key the rotation was driving, but leaves `state.rotation` pointing at the old schedule id — `isRotating(scheduleID:)` (`LockScreenService.swift:643`) still reports `true`. The scheduler's own driver, `driveLockScreenRotation` (`Store.swift:1146-1183`... — see also 1162-1163), trusts that flag alone to decide `stageRotationStep` vs. a fresh `beginRotation`; since it still reads `true`, every subsequent tick just hard-links a new video file behind the same fixed store id (`LockScreenService.stageRotationStep`, `LockScreenService.swift:675-682`/`1051-1058`) — a store id the Apple wallpaper store no longer references after the manual overwrite. No code path re-validates that assumption: `healIfNeeded`'s orphan check (`LockScreenService.swift:181-193`) only fires when the *scheduler* has stopped running the schedule (`runningRotationIDs` no longer contains it), which is not the case here — the playlist is still running, only its store ownership was hijacked. Stopping the playlist first calls `endRotation()` (`LockScreenService.swift:692-702`), which does clear `state.rotation`, which is why that ordering works.

Confirmed by tracing all three call sites end-to-end (manual apply → store write → next tick), not by a runtime timing reproduction.

**Fix**: `LockScreenService.apply(...)` now clears `nextState.rotation`/`nextState.preRotationSelections` whenever a non-rotation apply runs while a rotation pointer is still set (`LockScreenService.swift:515-528`). Only one rotation can be active app-wide, so any manual apply that reaches this function by definition supersedes whatever rotation was running. Clearing the pointer — rather than restoring the old pre-rotation snapshot, which is what a real `endRotation()` does — is deliberate: the manual apply's own new selection should stand, and the next scheduled tick now sees `isRotating == false`, so `driveLockScreenRotation` calls `beginRotation` again fresh, snapshotting the manual choice as rotation's new baseline. This is self-healing: the schedule's own next tick repairs the orphaned pointer without the scheduler or the UI needing to know anything happened.

**Not independently unit-testable**: same constraint as D11/D12. Covered by a manual check added to 8.10's scope: start a playlist, manually apply a different wallpaper mid-rotation, confirm the play indicator's next tick updates the lock screen again (rather than silently staging behind an orphaned id).

### D14: A manual apply must stop the schedule it would otherwise be overwritten by

**The bug**, reported by the user 2026-09-11 after D13 shipped: the situation got *worse*, not better. A manual apply to any surface/mode no longer reaches the lock screen at all (D13's self-heal made the scheduler's very next tick re-claim the store immediately), and — separately — the running playlist/automation's "play" indicator never turns off, even though the user's manual apply is understood to supersede it.

Root cause: nothing in `Store.applyWallpaper` (formerly `Store.swift:993-1024`) ever stopped an active schedule. D13 fixed the *pointer* orphaned by a manual apply, but the schedule itself kept running — its next tick (interval as low as ~10s) drives `driveLockScreenRotation` again and stages a fresh video behind the (now correctly self-healed) rotation id, silently reverting the manual apply. D13 alone was necessary but insufficient.

**Fix**: `applyWallpaper(_:mode:target:surface:fromSchedule:)` gained a `fromSchedule: Bool = false` parameter. When `false` (a genuine user-initiated apply — the only way `setWallpaper`, the public entry point called from `PreviewView.swift:673` and `MenuBarView.swift:199`, invokes it), it stops whatever schedule is active first, via the already-correct teardown pipeline: `if activePlaylist != nil { stopPlaylist() }` / `if activeAutomation != nil { stopAutomation() }` (both existing `Store` wrappers around `AutomationScheduler.stopPlaylist()`/`stopAutomation()` + `syncScheduler()`, which already tears down the lock-screen rotation correctly via `LockScreenService.reconcileRotation`).

Critically, `applyScheduledStep` — the scheduler's own per-tick driver — also reaches this same function for its desktop half (it used to call the public `setWallpaper`). Routing the scheduler's own tick through the stop-guard would have made every schedule stop itself on its first tick. Fixed by having `applyScheduledStep` call `applyWallpaper` directly with `fromSchedule: true`, skipping the stop guard entirely; the scheduler's own apply path is otherwise untouched.

**Not independently unit-testable**: same constraint as D11-D13 (`AppStore` is not driven from a fake clock). Covered by a manual check added to 8.10's scope: apply a single wallpaper while a playlist/automation is running and confirm both that the lock screen actually updates and that the schedule's play indicator turns off.

**Race condition found and fixed during independent review (Codex, 2026-09-11)**: the first version of this fix called the public `stopPlaylist()`/`stopAutomation()` wrappers, which end in `syncScheduler()`'s fire-and-forget `Task { await lockScreen.reconcileRotation(...) }`. Left un-awaited, that teardown (which can run `endRotation()` and restore the pre-rotation selection) could race the manual apply's own `lockScreen.apply(...)` write immediately below it — potentially reverting the very choice the user just made, undermining D14's own fix. Corrected: the guard now calls the scheduler's internal `stopPlaylist()`/`stopAutomation()` directly (not `Store`'s public wrappers) and mirrors `syncScheduler()`'s bookkeeping inline, `await`-ing `lockScreen.reconcileRotation(...)` itself before continuing — so any teardown is guaranteed to finish before the manual apply writes its own selection. `Store.stopPlaylist()`/`stopAutomation()` (the UI Stop button's path) are unchanged.

### D15: The lock-screen catch-up hook must not re-drive a paused rotation

**The bug**, reported by the user 2026-09-11: pausing a playlist and locking the screen does not freeze lock-screen playback; unlocking resumes playback on its own, with no play button pressed.

Root cause: `restageLockScreenRotationOnLock()` (`Store.swift`, the `com.apple.screenIsLocked` observer's handler) re-stages the current rotation step on every lock event unconditionally. Unlike the scheduler's own `reevaluate`/`fire`/`schedule`, it never checked `isPaused` (`Store.swift:948`, `config.paused ?? false`) before doing so — so locking (and, symmetrically, the same staging firing again on unlock) re-drives playback regardless of the user having paused the schedule.

**Fix**: added `guard !isPaused else { return }` at the top of `restageLockScreenRotationOnLock()`, using the same `isPaused` property `syncScheduler()` already consults (`Store.swift:679`, `:682`).

This guard prevents the catch-up hook from *restarting* playback on unlock. The separate question of why the lock-screen video kept *playing* while already paused and locked is D16 below.

### D16: A covered surface acquired without an explicit "locked" mode ignores the pause preference

**The bug**, same 2026-09-11 report as D15: pausing a playlist and locking the screen does not freeze the lock-screen video — it keeps playing.

Root cause, confirmed by tracing the extension's live-update path end to end: `Store.setPaused` → `LockScreenService.setLockScreenPlaybackPaused` (`LockScreenService.swift:767-771`) correctly writes `pauseLockScreen` to `muro-prefs.json` and posts a `preferences-changed` notification, which the extension *does* observe live (`ExtensionPreferences.swift:30` → `reloadAndApply()` → `applyCurrentPlaybackPolicy()` → `renderer.pause()`, `RendererState.swift:479`) — the earlier hypothesis that the extension only reads the preference at player-restart time was wrong. But that live-update path only touches surfaces that already exist in `active` at notification time. The user pauses while unlocked, so the lock-screen surface does not exist yet — macOS creates it on lock and tears it down ~15s after unlock. It is born later, in `acquire` (`main.swift:297`), which asks `RendererState.shouldPlayNow(mode: info.presentationMode, ...)`.

`shouldPlayNow` (`RendererState.swift:436-440`, before this fix):
```swift
if mode == "locked" { return !ExtensionPreferences.shared.pauseLockScreen }
if ScreenState.isCovered() { return true }
```
`pauseLockScreen` was only consulted when `mode == "locked"`. If the `acquire` request arrives with `presentationMode` nil/"default" — which `ScreenState.swift`'s own docstring documents happens on the first acquire after a restart/login, or on a race between `acquire` and the `com.apple.screenIsLocked` notification — but the screen is physically covered (locked, or the login window), the second line's unconditional `return true` wins without ever checking the pause preference.

**Fix**: merge the two branches so `ScreenState.isCovered()` (which is only true for a locked screen or the login window, never the screen saver or an ordinary desktop — see its docstring) is gated by `pauseLockScreen` exactly like `mode == "locked"` already was:
```swift
if mode == "locked" || ScreenState.isCovered() { return !ExtensionPreferences.shared.pauseLockScreen }
```
Single file (`RendererState.swift`), one line. `pauseLockScreen`'s default (`false`) still returns `true` here, so ordinary lock-screen playback on an unpaused schedule is unaffected.

**Not independently unit-testable**: `MuroWallpaperExtension` is an ExtensionKit target, not part of the SwiftPM package `swift test` runs — verified instead via `xcodebuild -project MuroWallpaperExtension.xcodeproj -scheme MuroWallpaperExtension -configuration Debug build CODE_SIGNING_ALLOWED=NO` (BUILD SUCCEEDED). Covered by the same manual check as D15 (8.10(g)).

**Known limitation, deliberately not fixed in this round**: `ScreenState.isCovered()` (`ScreenState.swift:29-38`) is also `true` at the login window (`kCGSessionLoginDoneKey` false), not only on an actually-locked screen. With `pauseLockScreen == true`, the login window now falls back to a still image the same way a locked screen does — and that still can be `DesktopStill.current(displayID:)` (`main.swift:181-185`), the *desktop's* cached still, rather than a frame of the lock-screen wallpaper itself, if the two differ and a desktop still happens to be cached. Before this fix the login window always played the video regardless of `pauseLockScreen`, so this is a real, new edge case — but a narrow one (requires pausing a lock-screen schedule and then fully logging out, not merely locking, while the desktop and lock-screen wallpapers differ), not something the user reported, and not worth the risk of a deeper `ScreenState`/`RendererState` change to a stability-sensitive extension file in this already-large correction round. Revisit as its own follow-up if a user reports it.

### D17: A pending rotation-begin can outlive the stop that should have reconciled it

**The bug**, reported 2026-09-11 after D14-D16 landed: stopping a playlist that covers the lock screen ("off") sometimes leaves the previous lock-screen wallpaper unrestored and the playlist's own video still playing indefinitely.

Root cause, found by independent review (Codex) and confirmed by tracing the code: `driveLockScreenRotation` (`Store.swift`, the branch that begins a fresh rotation) fires `Task { await lockScreen.beginRotation(...) }` without keeping a handle, without cancellation, and without anything awaiting it. `LockScreenService.apply(...)` (`LockScreenService.swift:484-652`), which `beginRotation` calls, computes `nextState` synchronously but only assigns it to `self.state` on its very last line (`LockScreenService.swift:650`), *after* a `Task.detached` that can take up to ~10s (three passes of store writes plus a `WallpaperAgent` restart and acknowledgement wait, see the comment at `LockScreenService.swift:549-556`).

If the user stops the schedule while that `beginRotation` is still in flight, `syncScheduler()` (`Store.swift:675-684`) calls `lockScreen.reconcileRotation(runningRotationIDs: [])` against `state.rotation`, which is still `nil` — the in-flight write hasn't landed yet. `LockScreenRotation.isOrphaned(rotationID: nil, ...)` returns `false` (it guards on `rotationID` being non-nil), so `endRotation()` never runs. Seconds later the pending `beginRotation` finishes and writes `state.rotation = scheduleID` for a schedule that has already stopped — nothing reconciles that write afterwards, so the rotation is orphaned permanently (until an unrelated future `syncScheduler()` call or a relaunch's `healIfNeeded` happens to catch it). The same race affects D14's manual-apply stop guard, which also ends in an inline `reconcileRotation` call.

**Fix**: track the in-flight begin as `private var lockScreenRotationBeginTask: Task<Void, Never>?` (`Store.swift:1130`), set only on the rotation-begin branch of `driveLockScreenRotation` (the stage-only branch never touches `state.rotation` and needs no tracking), cleared via `defer` when it completes. Both places that decide orphan status — `syncScheduler()` and the manual-apply stop guard in `applyWallpaper` — now `await` that pending task before calling `reconcileRotation`, so `state.rotation` always reflects the latest write before the orphan check runs. `driveLockScreenRotation`'s `isRotating(scheduleID:)` check was hoisted out of the `Task` to decide up front which branch to take (a synchronous, cheap read — no behavior change beyond deciding slightly earlier).

**Known non-issue, not defended against**: two overlapping `beginRotation`s for the same schedule (e.g. a tick and `restageLockScreenRotationOnLock` racing) would have the first one's `defer` clear the handle out from under the second. Pre-existing behavior — the code never distinguished this case before D17 either — and not reachable in the reported bug, so left as-is.

### D18: D17 tracked one pending begin, but not an overlapping one, a stale `running` snapshot, or two pre-existing restore/ordering bugs

A second independent review (Codex, 2026-09-11, of commit `3709966`) found D17's fix real but incomplete, plus two pre-existing bugs it judged blocking for reopening the PR. All four below were confirmed by re-reading the exact lines cited.

**1. `syncScheduler()`/the manual-apply guard captured `running` before waiting, then reconciled against the stale copy.** `let running = runningLockScreenScheduleIDs` ran before `await lockScreenRotationBeginTask?.value`; if a schedule was stopped and then reactivated *during* that wait, the reconcile still used the pre-wait (empty) set and could tear down the just-reactivated rotation. Fix: read `runningLockScreenScheduleIDs` again, fresh, immediately before the `reconcileRotation` call — not before the wait.

**2. D17's `defer` cleared `lockScreenRotationBeginTask` unconditionally, so a second `beginRotation` (e.g. `restageLockScreenRotationOnLock` firing while a tick's begin was still in flight) could have its handle wiped out from under it by the *first* task's completion, leaving nothing for a subsequent Stop to await.** Fix: added `lockScreenRotationBeginGeneration: Int`, bumped each time a new begin task is created; each task's `defer` only nils the shared handle if the generation it captured is still current. `syncScheduler()` and the manual-apply guard changed from a single `await pendingTask?.value` to `while let pending = lockScreenRotationBeginTask { await pending.value }`, so they keep draining until whichever begin is actually current has finished, however many were chained.

**3. Pre-existing, confirmed blocking by Codex — `endRotation()`'s restore loop wrote snapshot entries in unordered dictionary order and skipped every `__none__` (explicitly-removed) entry.** `AppleWallpaperStore.applyChoice` treats `targetKey == "all"` as "every node, unconditionally" (`AppleWallpaperStore.swift:221`), so writing `"all"` after a per-display exception silently overwrote it, and a display that had no wallpaper before the rotation (`__none__`) never got that state back — it kept whatever the rotation left there. Fix: order the restore so `"all"` (if present) is written first as the baseline, then every other key as an override on top of it; entries whose value is `__none__` now call `restoreWallpaperStores(targetKey:surface:root:)` (the same function `remove()` uses) instead of being skipped, so an explicit removal is actually restored.

**4. Pre-existing, D14's `applyGeneration` ticket was issued *after* awaiting the stop-guard's teardown, not before.** An apply that had to wait through a long schedule teardown could receive a *higher* ticket than a second, later apply that didn't have to wait — inverting "last request wins". Fix: moved `applyGeneration += 1; let myApplyGeneration = applyGeneration` to the top of `applyWallpaper`, before the `fromSchedule` stop-guard block, so the ticket reflects call order, not teardown latency.

**Deliberately out of scope**: `driveLockScreenRotation` re-entering the begin branch while a begin is already pending for the same schedule (e.g. two `restageLockScreenRotationOnLock` calls close together) still starts a second, redundant `beginRotation` rather than being suppressed — wasteful but no longer unsafe now that (2) tracks and drains every chained begin correctly. Preventing the redundant call itself would change `driveLockScreenRotation`'s behavior beyond what this bug requires.
