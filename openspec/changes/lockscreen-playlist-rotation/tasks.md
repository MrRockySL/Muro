- [x] 8.16 Found from user report 2026-09-11: manually applying a wallpaper "to all displays" and then immediately starting an Apply-to=All playlist produces no visible change at all, on either surface. Root cause and fix: D12 in `design.md` — `applyWallpaper` has no serialization between overlapping calls; a manual apply's deferred `applyAssignment` (delayed behind an `await lockScreen.apply(...)` loop that can take several seconds) can finish after a playlist's own first-step write and silently revert both surfaces. Not runtime-confirmed (only via code tracing) — see D12 for the honesty caveat. Fix: add a monotonically increasing `applyGeneration` ticket in `Store`; `applyWallpaper` captures it at entry and every state-mutating write point (the per-surface lock-screen loop, the trailing `applyAssignment`) bails out if superseded by a newer call. Single file (`Store.swift`), one function. @worker:free

- [x] 8.22 Found from user report 2026-09-11 (after 8.18-8.21 were installed): stopping a playlist that covers the lock screen ("off") sometimes leaves the previous lock-screen wallpaper unrestored, with the playlist's own video stuck playing indefinitely. Root cause and fix: D17 in `design.md`, found by independent review (Codex) and confirmed by tracing the code — `driveLockScreenRotation`'s rotation-begin branch fired an untracked, unawaited `Task` calling `beginRotation`, whose `LockScreenService.apply(...)` only writes `state.rotation` on its very last line, up to ~10s after starting. Stopping the schedule while that write was still pending made `reconcileRotation` read a stale `state.rotation == nil`, skip `endRotation()`, and let the pending write land afterwards with nothing left to reconcile it — orphaning the rotation permanently. Fix: track the pending begin as `lockScreenRotationBeginTask`; both `syncScheduler()` and the 8.21 manual-apply guard now `await` it before calling `reconcileRotation`. Single file (`Store.swift`). @worker:free
